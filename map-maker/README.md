# Map Maker

Battlemaps for Foundry, generated by Claude as code. Each map is a Node script that writes an SVG. Headless Chrome then renders the SVG to a PNG at any size.

This folder holds the tooling and what we learned building it (2026-10-30).

## Quick start

```sh
cd map-maker
node maps/palace-keep.js          # writes output/palace-keep.svg and output/palace-keep-walls.json
./render.sh output/palace-keep.svg 140   # writes output/palace-keep-140px.png
```

- Maps use **100 SVG units per 5-ft square**. The second argument to `render.sh` is pixels per square. Foundry maps usually want 100 to 140.
- Each script takes an optional seed: `node maps/forest-shrine.js 12` gives a different random layout of the same scene. The default seed is 7.
- `output/` is git-ignored because everything in it can be regenerated. `gallery/` keeps a copy of each map's SVG, which opens in any browser.
- Needs Node and Chrome. No npm packages. `render.sh` runs on macOS and Linux/WSL: it uses Google Chrome on a Mac, `google-chrome`/`chromium` on PATH, or the Chrome that `agent-browser` installed (`~/.agent-browser/browsers/chrome-*/chrome`). Set `CHROME=/path/to/chrome` to override.

## The maps

| Script | Size | What it is |
|---|---|---|
| `maps/forest-shrine.js` | 30 x 20 | Autumn forest clearing with a ruined chapel, a standing-stone ring around an altar, and a stream with a log bridge. Daylight. |
| `maps/burning-palace.js` | 30 x 20 | Burning imperial palace at night. Throne hall with columns and a dais, a collapsed wing on fire, a garden wing, and a forecourt with a barricade. |
| `maps/palace-keep.js` | 44 x 32 | Multi-room palace dungeon for PF2e, built in defensive layers (see below). Night, lit by braziers. |

The SVGs are in `gallery/`. Open one in a browser to see the map, or run `render.sh` on it for a PNG.

### Palace keep: room flow

The keep is built so the party clears it in layers and can rest between them.

- **Main route:** gatehouse, then long gallery, then banquet hall, then courtyard, then antechamber, then throne room.
- **Side rooms:** barracks, library (with a shrine), storeroom, and captain's quarters. The quarters have a secret door into the throne room for a flanking route.
- **Rest spots:** the library shrine, the storeroom and the quarters are dead ends off the main route.
- **Terrain ideas:** tables and fallen chandelier glass in the banquet hall, the deep reflecting pool in the courtyard, hedges and statues for cover, fire trenches flanking the throne room carpet. These are suggestions. The GM decides how they play.

The keep is drawn on a square grid (`grid[y][x]` holds a floor material or `null` for rock). Walls are drawn wherever floor meets rock, so the wall data is exact.

## Into Foundry

Every script writes `output/<map>-walls.json` as `{walls, doors, lights}`:

- **walls**: segments in SVG units. The exporter joins segments that share an end into long wall lines.
- **doors**: `[x, y, horizontal, length, kind]` in squares along a cell edge. `kind` is optional: `great`, `secret`, `locked`, `portcullis`.
- **lights**: `{x, y, range, color, anim?}`. `x`/`y` in SVG units, `range` in squares (dim radius; bright is half), `color` as `AARRGGBB`, `anim` an optional Foundry light animation. The scripts record one wherever they draw a fire, brazier, candle or glow.

### Native Foundry scene (use this)

```sh
node maps/palace-keep.js
node export-foundry.js palace-keep 140          # add --dark 0.6 for real darkness, --name "..." to rename
```

This writes `output/palace-keep.foundry-scene.json` and copies the map image to `~/foundrydata/Data/map-maker/palace-keep-140px.webp` (`--data-dir` to change). In Foundry: Scenes sidebar → **Create Scene** (any name) → right-click it → **Import Data** → pick the JSON. No modules needed.

The scene arrives with its size, grid, background, walls, lights and **every door type**:

| Kind in the walls JSON | Becomes in Foundry |
|---|---|
| normal, great | Door, starts **open** (the art draws them standing open) |
| secret | **Secret door** (only the GM sees it), closed |
| locked | Door, **locked**: players can't open it until the GM unlocks it |
| portcullis | Door, closed, **see-through**: sight, light and sound pass the bars; movement is blocked |

- **Lighting:** the maps have their light and dark painted in, so scenes import fully lit. `--dark 0.6` turns global light off and sets darkness so only the map's light sources (and darkvision) light it.
- **Lights:** braziers and fires get Foundry's `torch` animation; a light can name its own (`anim: 'pulse'` on the keep's arcane ring). They are kept **faint** (alpha 0.1, luminosity 0.2) because the art already paints each glow; at Foundry's default strength they stacked on the painted glow and bleached the throne room's arcane ring to white. This works lit (warm glow, flicker) and with `--dark` (pools of light in a dark keep).
- **Image** is WebP (about 1.2 MB for the 44 x 32 keep at 140 px, against ~30 MB as PNG), which matters when players load it from a remote server.
- The image must be in the data folder of the Foundry that imports the scene. For a remote server, copy `Data/map-maker/` across with the world.
- **Import quirk:** v14 keeps the background on the scene's level, but Import Data still migrates the old top-level `background` into the level and blanks the level's image when that field is missing. The exporter writes both.

**Tested in Foundry v14 (2026-10-30):** the palace keep imported through Import Data with 103 walls, the secret door as a GM-only secret door on the drawn seam, both portcullises see-through on the drawn bars, the other 8 doors open, and 28 lights. Light strength was then compared across five versions (lit/dark × default/faint/no lights) and Pax picked faint lights, lit by default and `--dark 0.6` for dungeons where darkness matters.

### UVTT (.dd2vtt) for other VTTs

```sh
node maps/palace-keep.js
node export-uvtt.js palace-keep 140     # writes output/palace-keep-140px.png and output/palace-keep.dd2vtt
```

The `.dd2vtt` file is the map image plus its walls, doors and lights in one file (the Universal VTT format). In Foundry, enable the **Universal Battlemap Importer** module (`dd-import`, v6.1.1 is verified on v14), click its button in the Scenes sidebar, and pick the file. The scene arrives with walls, doors and lights placed.

How the importer reads the file (checked against its source, `ddimport.js`):

- Light **range** is the dim radius in squares; bright light is half of it. Braziers use 8 (40 ft dim, 20 ft bright, like a torch), candles 2.
- Every door imports as a normal closed door. **It has no secret-door type**, so after importing the keep, switch its secret door (captain's quarters into the throne room) to *Secret* in Foundry. The portcullises also come in as plain doors.
- Doors the art shows standing open still import closed. Open them in Foundry if you want them open.
- It never reads `objects_line_of_sight`, so anything solid has to go in the walls.
- It ignores `environment`, so set the scene's darkness yourself. The night maps already have their darkness painted in.
- The importer shrinks any map wider or taller than 11,000 px. The 44 x 32 keep at 140 px per square is 6,160 x 4,480, well inside.

The exporter was checked against the walls JSON: every wall point in all three maps lands on an exported wall line and nothing extra was added.

**Tested in Foundry v14 with dd-import 6.1.1 (2026-10-30):** the palace keep imported with all 103 walls (no zero-length ones), 11 openable doors sitting exactly in the drawn doorways, and 28 lights (braziers 40/20 ft orange, the arcane ring 30/15 ft purple). On screen the wall lines follow the stone edges of the art.

## Matching another map set's colours

`tools/color_match.py` measures colours so a new map can sit next to published maps (it needs numpy, scipy and Pillow; the `dnd-transcription/.venv` has them):

```sh
PY=dnd-transcription/.venv/bin/python
$PY -I map-maker/tools/color_match.py stats ref1.jpg ref2.jpg map-maker/output/guild-hall-140px.png   # brightness, saturation, contrast side by side
$PY -I map-maker/tools/color_match.py palette ref1.jpg --k 12                                          # main colours as hex
$PY -I map-maker/tools/color_match.py sample ref1.jpg 1640 1640 14 14                                  # exact colour of a spot (x y w h)
$PY -I map-maker/tools/color_match.py materials map-maker/output/guild-hall-140px.png --ref ref1.jpg   # each of our colours vs the nearest ref colour
```

The guild hall (`maps/guild-hall.js`) was matched to Snowy's Five Toe Cove maps this way. The first draft was about 50% more saturated (chroma 32 vs 21) and lighter (L 60 vs 49–54); after swapping in sampled material colours it measured L 54, chroma 20.6. Snowy's style: thin wobbly black ink, flat watercolour fills, earthy muted colours (grass `#6a8b59`, dirt `#bda07e`, table wood `#a88963`, stone `#79776c`).

## What we tried and learned

### 1. Researching AI map tools

- **Foundry MCP Bridge** (free, MIT) generates battlemaps from a prompt with a local ComfyUI model and drops them into a scene. Its README only mentions Claude Desktop and asks for a GPU with 8 GB+ of VRAM. We did not install it.
- **Procedural generators** (Watabou's One Page Dungeon, donjon) export JSON that community tools turn into Foundry walls. The walls are exact, but the art is plain.
- **Point-and-click apps** (Dungeondraft, Dungeon Alchemist, Inkarnate) can't be driven by an AI. Dungeon Scrawl only exports walls on Pro.

### 2. Codex image generation

Codex CLI is installed and logged in with ChatGPT, so image generation costs nothing extra. The call is:

```sh
codex exec --skip-git-repo-check -C <out-dir> -s workspace-write \
  -i <reference1.jpg> -i <reference2.jpg> "<prompt>. Save the result as map.png"
```

- **It follows a scene description well.** Every feature we asked for showed up in the right place.
- **First try was not top-down.** Standing stones and walls were drawn slightly from the side. The fix was adding two reference maps drawn straight from overhead (labelled "camera reference") and spelling out the rules in the prompt: "orthographic plan view, no vertical surfaces visible, pillars shown only as their top face with a drop shadow." The second try was properly top-down.
- **Resolution is the hard limit.** Output tops out around 1536 x 1024. That's about 51 pixels per square on a 30 x 20 map, and about 33 on the 44 x 32 keep. Foundry wants 100 to 140, so Codex output needs an upscaler before it's usable.
- **No walls.** The image has no wall data. They have to be placed by hand.
- We used free 2-Minute Tabletop maps (CC BY-NC 4.0) as style references. They are not stored here. Download them again if needed.

### 3. Hand-coded SVG (this folder)

- **Strengths:** exact grid alignment, any resolution with no blur, wall data for free, consistent lighting, and precise edits ("move the altar two squares north" is a one-line change).
- **Weaknesses:** organic things (trees, ferns, rubble) look cartoonish next to painted art.
- **Techniques that made the biggest difference:**
  - SVG noise filters (`feTurbulence` plus `feDisplacementMap`) for hand-drawn wobbly edges and leafy canopy outlines.
  - Layered fills for trees: an ink outline, then shade, mid and highlight layers shifted toward the light, plus small "leaf cluster" arcs.
  - Soft blurred drop shadows, all offset the same way (light from the northwest).
  - Mottled noise overlays with `mix-blend-mode: multiply` for ground texture.
  - Glow circles with `mix-blend-mode: screen` for fire and candle light, over a dark blue "night" multiply layer.
- **Mistakes that bit us, so we don't repeat them:**
  - `<symbol>` with a `viewBox` and no width/height renders at full map size. Use a plain `<path id>` inside `<defs>` for reused shapes.
  - Small shapes placed close together read as faces: two candles plus a stain on the altar, and arc strokes on trees that looked like closed eyes. Check a zoomed crop after each render.
  - Thin straight white lines meant as birch branches read as stick arrows. Removed.
  - Rotating long objects can push them through walls. Check props near room edges.
  - Changing anything that calls the random generator shifts every random value after it, so colors and positions elsewhere can change.

### 4. Combining them: SVG layout, Codex paint

We gave Codex the rendered keep as the layout and the style maps as references, and told it to keep every wall and object in place. It did. Overlaying the result on the original showed no doubled walls at 1600 pixels wide, so the walls stayed within about a tenth of a square. That means the SVG wall data should still line up.

The result had richer textures, but Pax preferred the original SVG style. It also inherits Codex's low resolution. **We're going with the SVG maps.**
